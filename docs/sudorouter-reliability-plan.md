# SudoRouter 可用性改进与后续 HA 升级方案

更新：2026-11-15。任务：AVAIL-01。

## 当前方向与状态

当前优先保留单台 VM，完善发布、备份、恢复和账务正确性。永久双机、托管
PostgreSQL HA、托管 Redis HA 和负载均衡的扩容方案暂缓采购，保留为以后升级的选项。
本文件是当前方案入口；运行证据和任务进展仍在 Ladder，避免两份设计分别演进。

用户确认实施顺序后，本轮已接通单机自动 CD、加密异机备份和隔离恢复，并部署账务
退出窗口改进。源码合并、生产部署和实际验收分别记录；下面保存运行方式与能力边界。

### 2026-11-15 实施证据

| 项目 | 已验证结果 |
| --- | --- |
| PostgreSQL | 原 VM 身份向独立 Blob 存储写入 WAL-G 加密备份；流式接收 WAL，无需重启 PG。每天基础备份、每五分钟归档读回检查，保留七份完整备份及所需 WAL。 |
| 真实数据库恢复 | Azure 备份恢复到无外网 PG15.18：386 用户、77 通道、490 Token，用户/通道 ID 指纹匹配。188.62 秒就绪，首轮 180 秒超时也保留。另有隔离实验验证指定 LSN 前两条标记保留、第三条排除。 |
| 应用恢复 | 恢复库与原会话配置支持原镜像健康启动；新镜像对同一恢复库的原管理员登录和账务测试通过。独立 internal 网络，无公网端口和生产数据连接。 |
| ClickHouse | 独立加密日备份，Native/zstd 数据与 DDL；主库 40,886,785 行、电信库 264 行在隔离 CH24.8.14.39 实际导入，行数、全行哈希汇总和文件 SHA-256 一致。 |
| 自动 CD | 生产分支 CI 成功后，经 GitHub OIDC 操作现有 VM。临时副本运行新镜像，切流前真实 Sonnet 检查；排空升级、主实例业务检查、回切、移除副本。首次正常完成链路 235 次公网采样零失败。 |
| 失败恢复 | 首轮发现旧脚本不兼容合法的无额外缩进 Compose 列表；实际自动回滚，55 次公网采样零失败。现已修复并在切流前解析、校验完整候选 Compose。 |
| 账务 | 生产关闭内存批量写入；失败请求退款在 handler 返回前完成。新镜像在隔离 PG/本地模型桩下实测：成功扣费及失败退款在响应后 3.8 秒内强杀仍一致，SSE 遭 SIGTERM 正常排空、退出码 0；全量 CI 也覆盖原有 DB 写失败补偿和退款幂等回归。 |
| 独立检查 | Ladder 每小时检查公网、复制槽、备份时效、定时器和磁盘，失败进入 Actions 失败记录；不定时调用收费模型。通知是否到达邮箱取决于 GitHub 通知设置，不声称已验证邮件送达。 |

回执与最新状态：[Ladder 交付记录](https://github.com/elfenlieds7/ladder/blob/main/deploy/releases/2026-11-15-sudorouter-recovery-cd.json)。
部署使用与凭据边界见[自动 CD 说明](sudorouter-continuous-deployment.md)。恢复耗时是组件演练结果，
不等于整台 VM 故障后的恢复承诺。日志为每日快照，并有十分钟稳定截止线；PG 的五分钟
检查周期不是零丢数保证。Blob 使用 LRS，本阶段没有部署主机、数据库或区域自动故障切换。

关闭内存批量并完成退款等待，修复了明确的进程内窗口；仍未引入完整原子账本。
进行中的上游请求被强杀、数据库提交结果不明等情况仍需请求/用量对账，不能盲目重试非幂等退款。

### 当前阶段新增成本

没有新增常驻 VM、托管 PG/Redis 或 LB。新增固定计算费用为零。主日志单份加密包约
0.98 GB，按 14 天有效保留加 14 天删除恢复、当前大小不增长估算约 28 GB；仅这部分
Hot LRS 容量约 USD 0.5–0.6/月，PG/WAL、版本、操作及流量另计。

new-api 已核实为公开仓库，现用标准 GitHub-hosted runner 按
[GitHub 规则](https://docs.github.com/en/billing/concepts/product-billing/github-actions)免费。
Ladder 为私有仓库：小时检查按每次 1–2 分钟、USD 0.006/分钟保守估算约
USD 4.38–8.76/月，未抵扣账号免费额度。存储与运维检查合计暂按 **USD 6–12/月**
规划，低于此前 USD 20 设计目标；这是当前规模推算，不是已出账单，数据增长和执行
时长需继续按实际用量核对。此前永久 HA 报价保留在下文。

范围是 `sudorouter.ai` 的 **new-api**。FujiToken 使用 **sudoapi**，其生产发布和后台
worker 职责需要独立验证。ShareOne 保留在香港；本方案没有迁区、数据库升级或合并授权。
现有 VM 上其他应用保留，不能根据应用名称、低 CPU 或估算表行数判定应当退役。

## 为什么调整

11 月 14–15 日盘点的现有日本 VM 为 D2as_v6，2 vCPU / 8 GiB：七天平均 CPU
12.55%，峰值 73.24%；可用内存最低样本约 0.89 GiB。当前证据不足以支持为容量
立即扩容，也不足以支持把原 VM 缩为 4 GiB。

已定位的发布中断发生在容器切换窗口。现有临时 slave 接流、Caddy ETag 热切、
HTTP/SSE 排空和回滚已用于生产；固定窗口的 HTTPS 采样通过。它们改善单机发布，
不能防止整台主机故障。HA 的必要性还应依据可接受的停机、丢数窗口、客户承诺和
故障损失评估，不能只看 CPU 或流量。

电信版冗余 ClickHouse 已合并到隔离日志库，原容器已停止、备份和卷保留；相关
进程快照净释放约 418 MiB。VM 规格未变，因此目前没有产生 Azure 账单节省。

## 当前阶段：实施方式与验收要求

### 1. 核验最新生产和发布基线

- 拉取最新 `sudo/rc24` 和 Ladder `main`，对照实际运行镜像、源 commit、Compose、
  Caddy、数据库版本、后台任务角色和现有备份。先确认其他工作线是否已完成相关改进。
- 记录所有 new-api 域名、会话配置、授权路由、依赖启动时间和回滚材料的指纹。
  凭据留在 password-agent 和运行环境，仓库只记凭据条目名。
- 只读核对账单和现有存储可复用性；为备份保留量、告警、临时恢复环境单独报价。
  本阶段以新增不超过 USD 20/月为设计目标，尚不是核实后的总价或采购授权。

交付：一份脱敏基线和实际缺口清单，区分源码、部署、业务验收状态。

### 2. 先保证异机备份能恢复

- PostgreSQL 业务库优先。核验现有备份，再补异机存放、加密、保留策略、完整性检查
  和失败告警；密钥与数据分开保管。主机本地 dump、同盘快照和发布前备份不足以
  单独证明主机损坏后可恢复。
- 评估基础备份加 WAL 归档，以支持时间点恢复；只有异机归档链和恢复演练通过后
  才能声明有此能力。归档积压须告警并防止磁盘耗尽。需要重启 PG 才生效的配置须
  单独安排维护窗口，不随应用发版夹带。
- 独立处理 ClickHouse 日志、配置和恢复依赖，保留主网关与电信日志库的权限隔离。
  核验 Redis 哪些状态可由主库重建，不能直接假定全部缓存丢失均无影响。
- 在隔离目标恢复，核对业务数据、用户／token／渠道、日志、登录和应用启动；
  禁止测试环境运行支付、退款、定时扣费、账号刷新等生产副作用任务。
- 记录备份最新可恢复时间、实际丢数窗口（RPO）和恢复耗时（RTO）。具体可接受目标
  需结合业务对齐，以演练结果验收，不提前承诺零丢数或固定分钟数恢复。

交付：异机备份、失败通知、完整恢复步骤和一次真实隔离恢复回执。

### 3. 在现有单机流程上接通自动 CD

`.github/workflows/ci.yml` 在生产分支检查通过后调用 `sudorouter-cd.yml`，
复用 `docker-acr.yml` 构建精确提交的镜像。`docker-acr.yml` 仍支持手动构建，
[`sudorouter-release.yml`](sudorouter-offline-release.md) 保留离线发布包能力。

- 复用现有 CI、ACR 和 Ladder 的 `rollout_caddy_bridge.py` / `rollout_compose.py`，
  接通已通过适用 CI 的合并提交到发布流程。镜像固定 digest，并核对源码 revision；
  未通过 CI 或不能核对来源时不进入生产。
- 使用仅限目标部署资源的无人值守身份，优先评估 GitHub OIDC；不依赖运维浏览器
  长期登录。核对现有权限后再确定实际身份和凭据轮换方案。
- GitHub 与 VM 两端串行化发布；保留并发变更检测。临时副本仅接前台请求，
  后台任务保持单主，依赖容器保持运行。先核验 schema 允许新旧版本重叠。
- 按健康检查、接流、排空、主实例切换、业务检查、回切和清理的顺序执行。
  不兼容迁移单独处理；应用回滚不能恢复旧数据库来覆盖发布期间的真实账务。
- 失败候选在切流前拒绝；切流后失败按现有守卫恢复。不能安全恢复时保留服务副本
  和明确状态并告警，禁止盲目覆盖别人同时修改的 Caddy 配置。
- 验收正常发布、候选失败、自动回滚、并发发布拒绝、登录会话和长 SSE 请求。
  现有排空有时间上限，不承诺任意长度的流都能完成或断流后自动续传。

CD 没有新增常驻资源的需求。此前按私有仓库每月 30 次、每次额外 5–10 分钟
估算 USD 0.90–1.80；本轮已确认 new-api 是公开仓库，标准 runner 费用按上表更新。
ACR 镜像存储、artifact 保留及额外服务按实际用量核对。

交付：一次受控生产发布及业务回读、隔离环境的失败／回滚演练和可审计发布回执。

### 4. 验证异常退出后的账务恢复

- 实施前生产启用了进程内批量更新，默认周期为 5 秒，本轮发布已关闭。继续跟踪预扣、结算、退款、用户／
  token 额度、订阅、异步任务和缓存的实际数据路径；不能将某个批量开关视为所有
  路径均已持久化的保证。
- 在隔离环境覆盖批量写入前／后的进程终止、数据库写入失败、退款重试和重复结果，
  验证不漏扣、不重复扣、不重复退款，以及缓存能按权威数据恢复。
- 按核验结果选择最小改动：低负载下先评估缩小或关闭易丢的内存批量窗口；需要时
  再做持久化恢复记录。调整前验证写入压力、失败处理和三种数据库兼容性，不直接
  给生产关闭一个开关后就宣称账务可靠。
- 针对真实缺口补 service/model 回归；故障注入只在隔离环境执行。生产最终用一次
  限额的低价模型调用核对请求、实际用量和账务，记录实际费用并清理临时测试资源。

交付：各失败位置的预期和实际账务、恢复证据，以及完成对应代码与部署验收的回执。
这部分需要工程实现，不能用数据库 HA 代替。

## 后续 HA 升级备选：暂缓采购

以下是 2026-11-15 的组件估价，保留用于重新评估。实施前重新盘点和报价。
Japan East、USD 公开按需价、730 小时/月；不含税费和既有资源费用，不抵扣赠金。

| 拟新增资源 | USD/月 |
| --- | ---: |
| 一台 D2als_v6 应用 VM，2 vCPU / 4 GiB | 76.65 |
| 一块 64-GiB Standard SSD 系统盘 | 4.80 |
| 一个托管 PG HA 服务，主备各 2 vCore / 8 GiB，计算 | 356.24 |
| 托管 PG 存储，主备各 32 GiB | 8.83 |
| 托管 Redis B0 双节点 HA | 29.20 |
| Standard LB 前五条规则 | 18.25 |

流量、备份、监控、CD 等预留后，规划为新增 **USD 520–560/月**，不是账单上限。
保留旧 2核8GiB VM 兼任一个应用节点，只新增一台应用 VM；不在旧机之外再开两台。

若 B2als_v2 的持续接流、CPU 积分和内存验收通过，可每月少 USD 40.88：固定
USD 465.04，规划 USD 480–520。托管 PG 是一个由 Azure 管理主备的服务，已按
两份计算和两份存储计费，无需另加两台自管数据库 VM。

### 仍需解决的依赖

- 现有 VM 未声明可用区，应用跨可用区隔离尚未证明；本估价不含整个地域失效的容灾。
- 主 ClickHouse 仍在旧机，影响日志和替代应用启动。约 4084 万行日志压缩后
  1.75 GB、未压缩 17.52 GB，不能按压缩体积给 PG 选容量。
- 若实测支持迁入独立日志 PG 库，两份存储各 32→128 GiB 的差价为 USD 26.50/月。
  索引、读写负载、保留策略及所需计算尚未验收；此差价不是完整日志 HA 报价。
  若保留并复制 ClickHouse，需要另行设计和计价。
- 团队 sub2api 池仍依赖旧机；若干渠道使用 Docker 私有主机名，必须验证授权下的
  跨 VM 路由和替代上游。复制网关不能自动复制这些模型提供方。
- PG15 主业务库和团队 PG18 不能直接合并或降级；保留源版本兼容并隔离数据库／角色。
  托管 Redis 的区域容量、单端点、Lua／事务和键空间兼容性仍是迁移门槛。
- 自动切换、账务恢复、Redis 重建、后台单主、长流、备份恢复和下一次发版／回滚
  均需真实验收。数据库主备保护已提交事务，不能保存尚在应用内存中的增量。

因此 USD 520–560 是所列组件预算，完整服务 HA 的最终费用仍需补齐依赖方案。

### ShareOne 复用比较

现有 ShareOne 应用和 PG 都在香港，PG14、2核8GiB、128GiB，未启 HA。按当时规格
增加匹配备库约 USD 207.91/月；替代新日本 PG 可少约 USD 157.17/月，未计跨区域
网络。按上表 D 系列配置，条件方案固定约 USD 348.76/月，香港原主库继续属于既有
账单基线。版本升级、恢复和跨产品维护／故障耦合尚未验收，两 VNet 当时无 peering。

SudoRouter 接香港 PG 会增加跨区域数据库往返；只将 ShareOne 数据库迁日本也会
产生同类问题。应用一起迁区需要核验存储等依赖。因此当前保留两者地域和数据边界，
不提前抵扣任何假设的 ShareOne 资源退役节省。

### 重新评估的条件

出现以下情况时，重新比较停机／丢账损失、工程维护成本和持续云费用，再决定是否升级：

- 客户提出明确可用性、恢复时间或恢复点要求，现有恢复演练无法满足。
- 发生主机／区域故障，或恢复耗时导致不可接受的业务损失。
- 活跃业务和停机损失增长，足以支持常驻冗余与托管数据库的费用。
- 单机出现持续资源压力；同时分别评估扩容与故障冗余，避免混为一个需求。
